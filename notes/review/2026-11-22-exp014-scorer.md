## 1. The SCHED-vs-REF guard admits any value on keys REF lacks, and one of those keys switches off the filter (moderate)
`guard(..., allow_new=True)` (lines 62-79, 241) lets every key that exp005/006's REF lacks through at any value. Line 255
then prints only the key names, not their values. REF lacks nine keys:
- runOffLoss, selfDoes, larder, captureTaper, nuisanceCost, buckPrefValue, doePrefValue, cInitLo and cInitHi. (I
  compared exp005 REF_seed1's `_parameters` with exp011 FLAT_seed1's.)

`runOffLoss` is the switch for the mechanism exp014 tests. At 0, "the herder always brings it back, so spooking selects
nothing by loss" (params.js:266-267). Every one of exp011's 48 jobs ran at runOffLoss=0 (tools/exp011*.jsonl). An exp014
job list built from exp011's arguments would therefore pass the guard. So would a SCHED run at cInitLo 0.6, or with
larder on.

The real job list doesn't set any of these keys. The runs will carry params.js's defaults, and those are the values
the identity check reproduced exp005 under (runOffLoss 1, the rest 0, with cInitHi 1). So I expect no error in the
runs. The finding is that the guard couldn't catch one.

**Fix:**
- For keys REF lacks, require the identity value: a table in the tool (runOffLoss 1, cInitHi 1, the other seven 0)
  rather than "any".
- Print each such key with its value.
- Add a `selftest bad` case: SCHED with runOffLoss 0 must stop.

REFT and SCHEDT inherit the check through SCHED, so this one table covers all three arms.
